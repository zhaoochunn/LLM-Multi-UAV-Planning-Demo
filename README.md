# LLM Multi-UAV Task Planning Demo

A small, runnable demonstration of the validated software boundary between a mission planner and a multi-UAV execution backend.

## Overview

The original research prototype explored language-guided multi-UAV task planning. This reduced public MVP focuses on its software boundary: a planner-shaped component produces structured UAV assignments, Pydantic validates them, and a dispatcher translates each validated assignment into an execution action.

The current repository runs entirely offline:

    Representative instruction string
            ↓
    Mock Planner (deterministic; no LLM call)
            ↓
    Structured Task Generation
            ↓
    Pydantic Validation
            ↓
    Multi-UAV Task Dispatcher
            ↓
    Mock UAV Execution
            ↓
    Execution Results

MockPlanner does not interpret arbitrary natural-language instructions. It always returns a deterministic representative mission fixture; the supplied instruction is recorded only in the fixture's scene summary. This behavior demonstrates the planning-to-validation-to-dispatch software boundary without claiming real natural-language planning. The separate prompt reference documents how the original research prototype framed an LLM planner.

## Architecture

~~~mermaid
flowchart LR
    A["Representative instruction string"] --> B["MockPlanner"]
    B --> C["Deterministic mission fixture<br/>no language interpretation"]
    C --> D["MissionResponse JSON"]
    D --> E["JSON parser"]
    E --> F["Pydantic models and validators"]
    F -->|valid| G["Dispatcher"]
    F -->|invalid| H["Validation error"]
    G --> I["Per-UAV action mapping"]
    I --> J["MockBackend"]
    J --> K["ExecutionResult list"]
~~~

This is a centralized planner and dispatcher. Multiple UAV assignments do not imply decentralized agent reasoning or a general-purpose multi-agent framework.

## Key Features

- Deterministic representative mission fixture for inspecting the planner-to-execution boundary.
- Explicit MissionResponse, MissionPlan, and UAVTask data contracts.
- Strict Pydantic validation with forbidden unknown fields.
- Constraints for UAV identifiers, enumerated actions, headings, speed, and altitude.
- Cross-field checks for movement consistency, unique IDs, task count, and relay assignment.
- Structured task-to-action dispatch for multiple UAVs.
- Clearly labeled simulated execution results.
- Tests for valid plan dispatch and malformed task rejection.
- A prompt and few-shot configuration retained as documentation of the source research approach.

## Quick Start

Python 3.10 or newer is required.

~~~bash
cd public_demo
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python demo/run_demo.py --mock
~~~

Run the tests:

~~~bash
pytest
~~~

Neither command requires an API key or AirSim.

## Example

Input:

    Send two UAVs to inspect the forest for a missing person.

The instruction is not interpreted. The demo prints the same deterministic mission fixture under the label [MOCK LLM], with the instruction copied into scene_summary. One search task is:

~~~json
{
  "uav_id": "UAV_01",
  "role": "SEARCHER",
  "execution_mode": "DIRECT",
  "horizontal_movement": "HEADING",
  "heading": 0.0,
  "vertical_movement": "LEVEL",
  "search_pattern": "RADIAL",
  "priority_target": "person",
  "speed": 2.0,
  "altitude": 50.0,
  "target_area": "sector A",
  "constraints": {}
}
~~~

The JSON is parsed and validated as a MissionResponse. The dispatcher then maps all three tasks to backend actions:

    [VALIDATION] Mission plan accepted.
    [MOCK UAV EXECUTION] UAV_00: hold relay position at 100 m
    [MOCK UAV EXECUTION] UAV_01: search sector A using RADIAL at heading 0 degrees
    [MOCK UAV EXECUTION] UAV_02: search sector B using RADIAL at heading 180 degrees
    [RESULT] 3 UAV tasks simulated successfully.

These are mock results. They are not generated by GPT-4o and are not AirSim telemetry.

### Planner

MockPlanner.plan() returns a deterministic but schema-complete mission fixture. It does not parse or interpret its instruction argument. configs/research_prompt_reference.yaml records a prompt format and few-shot example derived from the original research prototype; neither reference configuration file is loaded by the current executable.

### Models, schema, and validation

schema/mission.py defines the plan contract and validation rules. schema/parser.py treats planner JSON as untrusted input and validates it before dispatch.

### Dispatcher and mock backend

Dispatcher.dispatch() iterates through validated tasks and maps relay and search assignments into action strings. MockBackend.execute() records each action as an ExecutionResult with status SIMULATED.

## Design Decisions

### Why structured task representation?

Natural language is flexible, while execution needs explicit identifiers, roles, movement modes, headings, search patterns, speeds, altitudes, and target areas. A typed mission object creates a clear boundary between those layers.

### Why validate before execution?

Planner output must not flow directly into an execution backend. Validation rejects malformed identifiers, unsupported values, inconsistent movement fields, duplicate assignments, incorrect task counts, and invalid relay configurations.

### Why separate planner and executor?

The schema decouples plan production from execution. A planner produces the contract; the dispatcher and backend consume only validated tasks. The mock implementation makes this boundary inspectable without external infrastructure.

### How does multi-UAV dispatch work?

One MissionPlan contains one UAVTask per vehicle. The centralized dispatcher converts each task to an action and sends it to the selected backend. In the example, UAV_00 receives a relay action while UAV_01 and UAV_02 receive separate sector-search actions.

## Limitations

- Mock mode does not call a real LLM and does not interpret arbitrary natural language; [MOCK LLM] is a deterministic representative fixture.
- Mock UAV execution is not AirSim execution and produces no flight telemetry.
- This public demo is a reduced subset of the research system.
- An online GPT-4o client is not included in the current public MVP.
- AirSim execution and visual perception code from the research prototype are not included or demonstrated here.
- PPO is not part of the main demo pipeline.
- Unreal Engine integration is not demonstrated in this public demo.
- The system is a centralized multi-UAV planner and dispatcher, not a decentralized multi-agent framework.
- There is no automated replanning, persistent memory, or production flight-safety guarantee.

## Research Background

This repository is a deliberately reduced public demonstration derived from a graduate research prototype on constraint-aware natural-language task planning for communication-constrained multi-UAV systems. It retains the core software boundary between planning, structured mission representation, validation, and execution dispatch while excluding experimental datasets, simulator assets, unpublished research details, and unrelated evaluation code.

The demo shows the engineering pattern of connecting model-produced task representations to a validated execution layer. It is not a paper-reproduction package and should not be interpreted as a production UAV control system.
